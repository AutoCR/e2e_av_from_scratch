BEVFusion-on-NAVSIM 3D 检测训练全流程报告

模型：BEVFusion（相机 + LiDAR 多模态 BEV 融合 3D 检测） 数据集：NAVSIM / OpenScene（5 类检测：car / barrier / bicycle / pedestrian / traffic_cone） 训练硬件：远程服务器 6 × NVIDIA RTX 3090（24 GB），6 卡 DDP 报告日期：2026-06-27

1. 摘要（Executive Summary）

本次工作的目标是：在前一次「从零训练（from-scratch）收敛极差」的基础上，定位问题、修复并完成一次健康的 BEVFusion 检测训练，最终用训练好的权重计算检测指标（mAP / NDS）与验证损失。

核心结论：

  • 诊断出旧训练失败的根因：缺少预训练权重热启动（warm-start）、学习率过低、训练轮数过多、并且检测头缺少 focal 负偏置初始化。
  • 完成修复并重新训练：热启动官方 10 类 nuScenes 权重 + focal 偏置初始化 + 学习率 2e-4 + 36 epoch 余弦退火，全程零失败跑完 170208 iter（36 epoch）。
  • 关键损失从「卡死」变为「持续下降」：loss_bbox 从旧的约 10 卡死降到约 5.4（验证集），loss_heatmap 从约 2.95 的平台缓慢降到约 2.6。
  • 评估阶段又发现一个隐蔽的致命缺陷：最终权重的检测头 BatchNorm running 统计量为 NaN，导致 eval() 模式下 零检测——但因为训练用的是 batch 统计量，训练损失全程「看起来健康」，监控无法发现。通过无梯度的 BN 重标定（recalibration） 修复后得到可用权重。
  • 最终评估（全量 4000 验证样本）：mAP = 0.0705，NDS（简化版）= 0.2297；其中 car 类 AP = 0.242（可用），稀有类（bicycle/barrier/cone）接近 0，反映 NAVSIM 严重的类别不均衡。
  • PDM 未计算：PDM 是规划（planning）指标，评估的是自车轨迹；BEVFusion 是纯检测模型，只输出 3D 框，不产生轨迹，因此 PDM 不适用。

2. 背景与问题定位

2.1 旧训练（from-scratch）的失败现象

前一次训练为「从零随机初始化、lr=1e-4、100 epoch」，跑满 36→100 epoch 后损失几乎不下降：

损失项 旧训练表现 含义
loss_heatmap 全程平台在 ≈2.95，100 epoch 几乎不动 模型几乎没学会定位目标
loss_bbox 从 ≈14 缓慢爬到 ≈8.5 后卡死，约 epoch 30 即停滞 框回归基本没收敛
loss_cls ≈0.23 分类项尚可

通过对 TensorBoard 标量的分解分析，确认问题不是数据量（训练集 85109 个样本，规模充足），而是训练配方（recipe）。

2.2 根因清单

  1. 没有热启动：BEVFusion 几乎从不「完全从零」训练。相机分支（SwinTransformer）与 LiDAR 稀疏卷积编码器都期望预训练初始化。
  2. 学习率过低：从零训练用 1e-4，是官方检测配方（2e-4，且配合预训练初始化）的一半。
  3. 训练过长：100 epoch 的余弦退火使后 70 个 epoch 在接近 0 的学习率上空转。
  4. 检测头缺少 focal 偏置初始化（评估前才补查到）：官方 BEVFusion 给 heatmap 输出卷积设了 bias = -2.19，本移植版漏了——导致重初始化的头一开始在每个位置都预测 sigmoid≈0.5，被海量背景梯度推向「处处预测背景」并卡死。

3. 优化与修复（按时间顺序）

整个过程遵循「先验证、再投入算力」的纪律：每个改动先用短跑（smoke run）验证，再决定是否提交全量训练；每个改动都记录进 CHANGELOG_TRAINING.md 并提交 git。

3.1 热启动路径（warm-start）

新增 pretrained_from 配置项：在建模时加载官方 10 类 nuScenes BEVFusion 权重，按形状过滤只丢弃与 5 类 NAVSIM 头不匹配的张量，从 iter 0 开始训练。

关键技术难点：

  • 6→8 相机差异不是障碍：BEVFusion 把相机数 N 折叠进 batch 维（img.view(B*N, C, H, W)），N 不出现在任何权重形状里，因此 nuScenes 的 6 相机权重可直接用于 NAVSIM 的 8 相机。
  • LiDAR 稀疏卷积权重布局不匹配：官方 checkpoint 以 [kD,kH,kW,in,out] 存储，而 spconv-cu120 的 .weight 是 [out,kD,kH,kW,in]。新增自校验的 permute：对 lidar 卷积权重尝试候选 permute，仅当 permute 后形状精确匹配才加载，否则丢弃——即使猜错布局也绝不会污染权重。

最终热启动加载 577 个 key（其中 21 个经 permute 重对齐），仅丢弃 5 个与类别相关的检测头输出层。

3.2 训练配方修正

配置 旧值 新值 理由
峰值学习率 lr 1e-4 2e-4 对齐官方检测配方
训练轮数 num_epochs 100 36 旧训练 epoch 30 即停滞，缩短避免空转
每卡 batch 4 3 batch 4 在 6 卡 DDP 下反传时 OOM；batch 3 留约 3 GiB 余量

3.3 检测头 focal 偏置初始化（关键 bug 修复）

诊断量化证明：loss_heatmap 卡在 ≈2.9 不是慢收敛，而是头塌缩进了「处处预测背景」的最优盆地（峰值置信度卡在 sigmoid≈0.04）。修复方法是给 heatmap 输出卷积加 focal 负偏置 bias=-2.19（标准 CenterPoint/TransFusion 技巧），使「预测背景」成为初始状态，梯度能量转而用于抬升真实峰值。

3.4 被排除的「伪 bug」

评估前的诊断中，单 batch 过拟合测试一度显示 bbox 中心回归（cx,cy）无法收敛，疑似 bug。但两路独立调查（静态分析 + 远程实测插桩）一致确认：

  • 中心回归路径与官方 TransFusion 一致，没有编码/坐标/梯度 bug。
  • 单 batch 不收敛是因为 匈牙利匹配在每步翻转（IoU 代价在初期≈0，加上同类目标过多导致匹配退化）；
  • 关键事实：远程 IOU3D_CUDA_AVAILABLE = True，真实 CUDA 训练中 IoU 代价是激活的，匹配稳定——所以这是诊断条件造成的假象，生产路径无 bug，无需改代码。

3.5 训练存活性保障（无人值守）

为支撑「本地电脑/会话关闭、服务器重启」三种失效场景下训练不中断：

  • 脱离会话启动（setsid nohup）：训练归属远程 pnc 用户，本机或会话关闭都不影响。
  • 服务器重启自恢复：@reboot cron + 幂等 autostart_train.sh + runner 的 last.pth 自动续训逻辑。
  • 每 epoch 保存 checkpoint（约 1 小时），崩溃/重启最多损失约 1 epoch。

4. 训练过程与损失曲线

最终训练于 6 卡 RTX 3090 上跑满：

  • 全局 batch = 18（6 卡 × 3），每 epoch 4728 iter，共 36 epoch = 170208 iter。
  • 全程约 25 小时，零崩溃 / 零 OOM；整个 170208 iter 中仅出现 1 次瞬时 loss-NaN（iter 23，被 runner 跳过）和 1 次孤立 grad-inf（iter 127350），均被自动吸收，无影响。
  • 采用约每 30 分钟一次的自动监控 tick（约 80 次），实时检查存活、损失曲线、磁盘、并按规则自主纠错。

5. 评估（无训练流程）

5.1 评估范围与可行性

用户要求用训练权重计算 eval-loss、mAP/NDS、PDM。经代码梳理：

指标 状态 处理
验证集损失 代码已有（_try_loss_eval），原因 OOM 被禁用 写独立脚本单卡 + 小 batch 运行
mAP / NDS 仓库无实现，但 GT 与推理路径都在 新写一个纯 torch/numpy 的 3D 检测评估器
PDM 不适用 PDM 评估自车轨迹，检测模型不产生轨迹，跳过

5.2 评估中发现并修复的致命缺陷：检测头 BatchNorm 统计量为 NaN

首次评估返回 零检测。插桩诊断定位到：最终权重 iter_170208.pth 的 6 个检测预测头分支的 BatchNorm running_mean / running_var 全为 NaN（共 12 个缓冲区），而所有模型参数都是有限值。

  • 为何训练全程没暴露：train() 模式下 BN 用当前 batch 统计量，忽略损坏的 running 缓冲区——所以训练损失一直健康，这是纯损失监控无法发现的隐性失效。
  • 为何 eval() 零检测：eval() 用损坏的 NaN running 统计量 → 预测全 NaN → 200 个 proposal 全被 score / 范围过滤丢弃 → 0 框。
  • 根因：很可能是 fp16 训练中某步 BN 统计量发散为 NaN（损失因 batch 统计量回退而仍有限）。

修复：BN 重标定（无梯度）——加载权重后，重置非有限的 BN running 统计量、设 momentum=None（累积平均），把 BN 模块切到 train 模式、其余保持 eval，在验证集上跑 300 次纯前向（无反传） 重新估计统计量，保存为 iter_170208_bnfix.pth。重标定后 6 个 NaN 模块 → 0，模型恢复正常输出检测框。

重要提示：原始 iter_170208.pth 评估为 0 mAP，后续任何推理/评估都必须使用 iter_170208_bnfix.pth。

5.5 评估结果的客观解读

  • 模型确实学会了检测：car 类 AP=0.242、平移误差 0.85 米，是一个可用的结果；全量评估有 35669 个真正例匹配。
  • 稀有类接近 0：bicycle / barrier / traffic_cone 的 AP 极低，反映 NAVSIM 数据严重的类别不均衡（实测一帧平均约 41 个框，但绝大多数是 car，4/5 类通道几乎总是空的）。
  • 定位为「中等水平的基线检测器」：可用，但尚不强；提升空间主要在稀有类与整体精度。

7. 结论与后续建议

7.1 结论

本次工作完成了从「诊断旧训练失败」到「修复配方与代码缺陷」「跑完一次健康的 36 epoch 训练」「定位并修复隐性 BN-NaN 缺陷」「给出可信检测指标」的完整闭环。最终模型是一个可用但中等水平的多模态 3D 检测基线：car 检测良好（AP 0.242），整体 mAP 0.0705 / NDS（简化）0.2297，瓶颈在稀有类与类别不均衡。

7.2 后续建议（按优先级）

  1. 训练侧加 BN-NaN 守护：在保存 checkpoint 时检查 BN 缓冲区是否含 NaN，并排查 fp16 路径（amp.py）作为 NaN 来源——否则未来 checkpoint 会重复这一隐性失效。
  2. 缓解类别不均衡：对稀有类做过采样 / 类别加权 / 复制-粘贴增广，提升 bicycle/barrier/cone 的 AP。
  3. 若要 PDM：需在检测之上构建规划模块（框 → 轨迹），是一个独立的工程，而非「再算一个指标」。
  4. 指标完善：如需与官方对齐，可补齐 NDS 的 AVE/AAE 项（需速度/属性 GT）。
